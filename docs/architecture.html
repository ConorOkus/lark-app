lark-app — how the pieces fit

One rule explains most of it: everything above the LarkCore seam knows nothing about bitcoin plumbing; everything below it knows nothing about screens. The app is currently a thin client — the wallet (keys, coins, channels) lives inside a barkd daemon it talks to over REST.

UI — Compose Multiplatform iOS + Android, one codebase

22 thin screens (Home, Pay, Get paid, Activity, Settings, Advanced…). They render one immutable AppModel and call intent functions. No logic, no networking, no bitcoin.

AppStateMachine one StateFlow<AppModel>

Owns navigation (hand-rolled route stack), keypad state, the backup countdown, hidden-balance masking, formatting. Collects the core's flows (balance, health, wallet-exists, channels) and re-renders the single model the UI shows.

⚿  LarkCore — THE SEAM

A small Kotlin interface: balanceSats · health · walletExists · channels · activity · receiveCode · send() · refresh() · createWallet(). Screens are provably core-agnostic: the same contract test suite runs against every implementation. Swapping what's below never touches what's above.

core/LarkCore.kt — chosen at compile time in CoreSelection.buildCore (CoreConfig)
today: FakeLarkCore (demo) or GatewayLarkCore (real, REST) M2 plan: lark-ffi — Rust bark+LDK in-process, keys on device

FakeLarkCore DEMO

In-process pretend wallet. No network, no funds. Drives the design's demo rail; default build flavor.

GatewayLarkCore GATEWAY

The real core. One 15s poll loop (balance, vtxos, history, tip, connected, channels) + long-poll notifications where supported. Health mapping (READY / TIDYING / STALE / OFFLINE), offline backoff, and the R16 identity hard-fail: wrong network or missing channel support → refuses to operate.

core/gateway/GatewayLarkCore.kt (~580 lines)
↓typed REST calls, every request through one AuthDecorator seam (NoAuth today; bearer token drops in)

BarkdApi compile-time variant

BarkdApiVariant selects which wire surface it speaks; BarkdCapabilities tells the core what exists so it degrades honestly (no mnemonic endpoint → real “words unavailable” notice, no notifications → pure polling, no bip321 → mint address + build URI client-side).

core/gateway/BarkdApi.kt · BarkdApiVariant.kt · BarkdDtos.kt — Ktor, specs vendored in docs/gateway/
↓  ↓HTTPS (loopback http allowed for local dev)

STOCK_0_4 → Second’s signet

barkd 0.4.0 daemon (runs anywhere) holding the wallet — keys server-side, connected to Second’s public Ark server ark.signet.2nd.dev. Lightning is bridged per-payment by the server’s node: no channels of your own.

proven live: create · faucet receive · LN send/receive · refresh round · unilateral exit

FORK_BETA6 → local mutinynet (LARK)

Greg’s forked barkd (0.1.0-beta.6) + forked captaind with embedded LDK. This is the differentiator: a real LDK Lightning channel funded by an Ark VTXO — instant, fee-less channel opens off-chain, with a trustless on-chain force-close escape hatch.

local stack: bitcoind (mutinynet) → postgres → captaind :3535 → barkd alice :3001 / bob :3002 — docs/gateway/local-mutinynet.md

Money lives server-side in both cases. The app displays and instructs; barkd signs and holds. That’s the M1 trade-off — M2 (lark-ffi) moves the wallet into the app process and flips custody to keys-on-device. The gold seam above is what makes that swap a two-file change instead of a rewrite.

Cheat sheet

Why a seam?
Three wallets, one app: demo (fake), thin client (REST → barkd), and the future in-process Rust core. The interface is the only thing all three share.
Why compile-time variants?
The two barkd surfaces (stock 0.4.0 vs the LARK fork) differ in routes, shapes, and abilities. CoreConfig picks mode + variant + URLs per build — no runtime probing of a fragile daemon.
Why is the fork special?
Only the forked captaind runs the channel bridge: LDK channels whose funding output is an Ark VTXO. Stock Ark bridges Lightning per-payment through the server instead.
Health, in one line
READY (all good) · TIDYING (round in flight, shows as Ready) · STALE (VTXO expiry near — “needs a moment”) · OFFLINE (unreachable / wrong identity / auth).
Trust model today
The gateway holds the seed. Fine for dev/testers on test networks; M2 flips it.
Testing model
A scriptable mock daemon (GatewayTestHarness) + fixtures spec-pinned to the vendored OpenAPI of each surface; 244 tests. The live stack is a smoke pass, never CI.
